# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Windows-only native overlay that shows Warframe squad peer info (platform, name, host status, and optional country/region/ASN) anchored to the bottom of the game window. It detects the `Warframe.x64.exe`/`Warframe.exe` process, tails `%LOCALAPPDATA%\Warframe\EE.log`, and renders a borderless, click-through, always-on-top window with a tray icon for exit. In the background it also saves mission loadouts as JSON, read out of the game's memory (read-only): each squad member's once EE.log announces that they joined and again whenever they change it, and our own every time EE.log shows it rebuilt. Four ordinary windows, each hidden until the tray menu opens it, show those loadouts with items named as the game names them, from the public export vendored as a submodule: `Loadouts` as a card per player, `Loadouts (full)` as a tall card per player listing every slot's mods, `Loadouts (6grid)` as six places in two rows of three for squads of six, and `History` as everyone we have shared a squad with before, beside statistics on what they played. A fifth, `Session (debug)`, shows the missions EE.log shows loaded lately and the one each squad member is tied to, which the history writes down with them when its session ends or they leave. Every word the overlay writes itself is in English, which is what it opens in, or in Japanese, which is what the windows were laid out against; the tray's `Language` menu picks between them, writes the choice down and starts the overlay again in it.

Privacy model (see README.md): log parsing and host detection are entirely local. If geo lookups are enabled (default), only the detected public IP is sent to `https://ipinfo.io`; results are cached on disk for 30 days. Loadout capture opens the game process with `PROCESS_VM_READ | PROCESS_QUERY_INFORMATION` only — it never writes, injects or hooks — and saves loadouts, with display name and platform, under `%LOCALAPPDATA%\synqark\WarframePeerOverlay\data\loadouts`; none of it is uploaded. Item names are embedded at build time, so looking them up sends nothing anywhere. EE.log contents and IPs are never logged or uploaded. `--no-geo` disables the external lookup entirely. The chosen language is the only other thing kept, in `settings.json` beside the loadouts.

## Commands

```powershell
git submodule update --init   # fetches third_party/warframe-public-export-plus (shallow); the build embeds item names from it
git submodule update --remote # moves it to the latest export after a game update; the next build picks it up
cargo build --release   # produces target\release\warframe-peer-overlay.exe
cargo run                # debug build + run (Windows only — uses windows-sys/tray-icon/winit)
cargo test                # runs all unit tests (every module has a #[cfg(test)] block)
cargo test <test_name>    # run a single test by name, e.g. `cargo test joins_member_ip_and_host_when_events_arrive_out_of_order`
cargo test --lib -- --ignored show_   # opt-in: pops a real desktop toast to verify notifications
cargo clippy --all-targets # lint
cargo fmt --all --check    # CI enforces this
```

The binary must be built/run on Windows — it links `windows-sys` APIs directly (window enumeration, positioning, process memory reads) and uses `tray-icon`/`winit` Windows integration.

CI (`.github/workflows/ci.yml`) checks out the submodule and runs fmt/clippy/test/build on `windows-latest` with `RUSTFLAGS: -D warnings`; keep all four green. Pushing a `v*` tag triggers `release.yml`, which attaches the exe to a GitHub Release.

## Licensing and game data

This is a personal-use tool with no plans to be published, so game-derived strings and data may live in the repository and be embedded in the exe. In particular, `third_party/warframe-public-export-plus` is a git submodule of [calamity-inc/warframe-public-export-plus](https://github.com/calamity-inc/warframe-public-export-plus) — Digital Extremes' public export, reorganised and completed, with no license of its own — and the exe embeds item names taken from it. The Unlicense in `LICENSE` covers this project's own code, not the submodule or the data drawn from it. Tests may use real game paths and names. `assets/icon.png` is original artwork drawn for this project (a four-node squad graph in the overlay's gold/navy palette).

What stays out of the repository is other players' data: tests build their own minimal loadout JSON and log lines, never a captured loadout or a log sample with real player names.

## Architecture

The app is a background monitor thread feeding a UI thread over an `mpsc` channel, with a strict pipeline for turning raw log lines into on-screen peer cards. Off to the side, a capture worker thread takes loadout jobs from the monitor, writes what it finds to disk, and hands each find back to the monitor for the loadout windows.

1. **`src/parser.rs` — `LogParser`**: a pure state machine over EE.log lines. It has no I/O; `process_line(&str) -> bool` returns whether the parseable peer state changed. It correlates several independently-arriving log line types (`AddSquadMember`, `Squad host address`, `Added remote player`, `VOIP: Registered remote player`, `Received ping from`) into a `Vec<Peer>`, because Warframe emits a peer's name, matchmaking ID, and IP on different lines in unpredictable order. `reconcile()` re-derives each peer's IP and host status every time new correlating data arrives; host detection falls back to "the locally logged-in user is host" only when no remote peer's IP matches `Squad host address`. Player names embed a private-use-area codepoint (e.g. `\u{e001}`) as a platform suffix — decoded in `parse_player_name`. It also keeps the loadout size each member's `ProcessSquadMessage received JOIN message from <name>, loadout: <N> bytes` line announces (`Peer::loadout_bytes`); that line arrives just before the member's `AddSquadMember`, so the size is held by name and applied in `reconcile()` like the ping IPs. For our own loadout it counts `BuildLoadOut for <local user>` lines (`own_builds`) — every change in the arsenal, leaving it, and loading into a mission rebuilds it — and remembers our platform from our own `AddSquadMember` (`local_platform`); neither is reset by `clear()`. A member who changes their gear after joining sends the squad their loadout again, which EE.log shows as `HandleSquadMessage from <address> LOADOUT` — once for the change and once more on leaving the arsenal — with no name and no size, and from an address that is the member's own only while we host: in a squad somebody else hosts, the host relays every member's messages, and the line carries the host's address whoever sent it. So they are counted for the squad as a whole (`loadout_messages`), which `clear()` does not reset. The game writes EE.log in bursts, so a line can land some ten seconds after the message it tells of.

2. **`src/geo.rs` — `GeoResolver`**: given a public IP, queries `ipinfo.io` for country/region/org, skips private/loopback/documentation IPs, and caches results (with a `fetched_at` timestamp, 30-day TTL) to a JSON file under the OS cache dir (via `directories::ProjectDirs`, `com.synqark.WarframePeerOverlay`). `looks_like_hosting_provider` matches the ASN org name against a hardcoded list of cloud/hosting providers to flag likely relay/VPN peers (`is_hosting`) — this is a heuristic, not a definitive VPN detector. Entirely bypassed when `--no-geo` is passed.

3. **`src/monitor.rs` — `spawn`/`run`**: owns the background thread. On a 500ms loop it: (a) polls `sysinfo` for the Warframe process, (b) if running, finds its main visible window's client rect via `EnumWindows`/`GetClientRect`/`ClientToScreen` (used by the UI to position the overlay under the game window), (c) tails `EE.log` by tracking a byte offset and only feeding *complete* lines to `LogParser` (partial trailing lines are buffered in `pending` until the next newline arrives — see `read_appended_lines`), (d) hands the capture worker every newly announced member loadout — once per name and size, never for the local user (`capture_requests`) — an update job for every member whenever `loadout_messages` has moved (`update_requests`: the line cannot say whose loadout it is, and the worker tells the member who changed theirs from the rest by whether their records moved) — and our own loadout whenever `own_builds` has moved (`own_request`; right after start-up that is immediately, as the log replay counts every rebuild so far) and a note job whenever EE.log shows somebody else's loadout rebuilt (`others_note`), then drains what the worker has captured, (e) resolves geo info for any new peer IPs via `GeoResolver`, and (f) builds a `Vec<PeerView>` (the parser's `Peer` plus resolved geo/UI fields) and the loadout window's `Vec<LoadoutView>` (`loadout_views`: ours always first — the latest own capture, else a placeholder from the parser — then every member still in the squad, each with whether the squad connects through them and where they connect from, matched to a capture by name *and* announced size, so a member who re-joins with other gear is not shown the old one — unless the worker has found the loadout they changed to since joining (`Captured::Update`, kept by name in `member_updates`), which stands in for the announced one until they leave or a JOIN capture brings a newer one; each member's card also carries the location resolved for their `PeerView`, which `loadout_views` takes by zipping the two, since both hold the same peers in the same order; a member's card goes when the parser drops them), and writes players into the `History` with the mission they were tied to: everyone in the squad whenever a session has ended (`MissionTracker::sessions_ended`), untying each as they are written down (`untie`) so that leaving afterwards writes nothing twice, and anyone who was in the squad a pass ago and is not now, if they are tied to a mission still — a member who left mid-session, whose tie the session's end did not reach (which the snapshot carries as an `Arc<[HistoryEntry]>`, cheap to clone into all four windows), and sends a `MonitorSnapshot` through the channel — but only when a signature (debug-formatted state) differs from the last sent snapshot, to avoid needless UI churn. How it is getting on rides along as a `Status` rather than a sentence, so the UI can tell `Monitoring` from the rest without matching on wording that the language changes; `Display` turns it into words through `lang::text`. State resets (log offset, parser, geo failure cache, requested and captured member loadouts and the changes found to them) whenever Warframe stops running; our own capture is kept. The log offset and parser also reset when the log file shrinks (log rotation).

4. **`src/loadout.rs` — capture worker**: a loadout lives in the game's heap as a NUL-terminated JSON string starting with `{"PlayerLevel":` (warframe and weapons with their mods, forma and levels, companion, archwing, operator, gear, focus). One pass over the game's committed, readable, non-code regions (`VirtualQueryEx`, then `ReadProcessMemory` in 32 MB chunks) collects every such string that ends in `}` right before its terminator and parses, counting identical copies (`census`). The game frees and commits pages while a pass reads, and a read that meets one page gone fails whole (`ERROR_PARTIAL_COPY`, nothing copied), so a chunk that fails is read again a page at a time with the missing pages left as zeros (`read_pages`); the same happens to the test process under parallel tests, which is what once made `reads_a_loadout_back_out_of_a_live_process` fail now and then. That serves every kind of job: a member's loadout is the string of exactly the size their JOIN line announced (`pick_member`); ours is picked by `pick_own`, trying in turn (`Reason`): the most-copied version the previous pass did not meet — the rebuild itself, which appears within the same second as `BuildLoadOut`, and also a version met long before, freed and built again, as when a weapon is changed back; the version whose copies grew most since the previous pass, since the arsenal copies ours dozens of times over on the way in; the version already taken for ours, while it is still in memory; and, only with none of those, the most-copied version. Copies alone cannot tell which is current: superseded versions are not reliably freed, and a recording of the game's memory showed an old loadout lingering in 18 copies for a whole session while the current one sat in 4 outside the arsenal, so taking the most-copied whenever a rebuild changed nothing (as leaving the arsenal does) put the old loadout back on our card. That is also why the worker remembers each version's copies at the previous pass of any job (`History::previous`) rather than every version it has ever met. At start, `recognise_saved_own` looks for the version `self_latest.json` holds, compared as JSON since the saved copy was laid out afresh, and takes it as ours, so a restart carries on from the loadout we had. Versions saved for members are never taken for ours, and neither is one ranked below us. `BuildLoadOut` fires for squad members too — the game builds their loadouts locally — so a version no pass has met is not ours by that alone, which is how another player's loadout used to be saved as ours. Two things tell them apart: `Job::Others`, a pass asked for as soon as EE.log mentions somebody else's rebuild, which takes their version in as met; and the mastery rank a loadout opens with (`mastery_rank`), since ours never drops below the last rank we saw (`own_mastery`, seeded from `self_latest.json`). When nothing clears that floor, `pick_own` reaches past it, so a wrong capture cannot lock ours out for good. Capturing by size, and our own loadout, involve no struct layouts or pointers, so a game update that moves memory around does not break them. A member's changes after joining are the exception. Their LOADOUT line gives no size, and the game keeps old versions of a loadout in memory for a long time, so the version is found through the game's own records instead: `referrers` finds every aligned word holding the address of a loadout string (the census notes where each copy lies), and `record_owner` reads the player a record belongs to as the player name nearest before that word, within `OWNER_REACH` (the game's record keeps it 88 bytes before, beside the account and matchmaking ids). A name is kept in place when short, or as an address followed by a length word whose top four bits are set, and is told from the rest of a record by the platform mark it ends in (`player_name`); taking the nearest keeps a row of records from being put to the player of the record before. A name in place is taken as the tail of a longer one only when the word before it is plain ASCII text (a number without small bytes in it is not), and the window reads one word past the reach so that a tail at its far end is never taken for a whole name. A record is read while the game may be filling it in, and one was caught holding a member's name and our own loadout — just as our game answered their LOADOUT with a message of its own — so a version is put to a player only when most of the records naming anybody on it name them (`records_naming`): our own loadout has dozens of records in our name, and one stray record does not outvote them. The game keeps one record per player that it updates in place, makes a new one for each loadout a player sends, and leaves old ones pointing at old versions, so `pick_update` takes the version most of a member's records point at among those that point somewhere else than at the member's last look (`MemberState::records`, first taken when their JOIN is captured), and nothing when nothing moved. Should a game update move a record's name out of reach or change how strings are kept, changes after joining simply stop showing, while the JOIN capture goes on as before. No offsets are assumed beyond the reach. A pass reads several GB and takes a second or two, hence the thread of its own: jobs arriving together share one pass, a member is retried every 2 s for 20 s, an update gets a second look when the first finds no record moved, the record search (a second sweep over the regions, about as long as the census) runs only when a member was just captured or has an update waiting, and our own rebuild gets a second pass when the first finds no version built or copied about since the pass before. Members are written as `<unix time>_<name>_<platform>.json`; ours only as `self_latest.json`, written aside and renamed over so a reader never sees half a file — an earlier copy of our own is of no use to anything, so none is kept. Members' are not kept for ever either: `discard_unkept` throws away every member file no `History` entry names, sparing whatever was captured after the last departure written down (a squad still together, whose members are written down only as they leave), and takes `self/` with it, the archive of our own rebuilds earlier versions left behind. Every file wraps the loadout with name, platform, size and capture time, in the order the game wrote it (`serde_json`'s `preserve_order`). Every find is also handed back over a second channel as a `Captured`, carrying the whole loadout as a `RawJson` — whose `Debug` is a hash, so the monitor's signature does not grow by tens of kilobytes a player — and a `Loadout` summary (`Loadout::from_json`): mastery rank, the `PostNewWar`/`PostOldPeace` quest flags, the warframe, secondary, primary and melee from `NORMAL` slots 0–3, the companion from `SENTINEL[0]` with its `KubrowName`, the auras (`AuraName`, then `ExtraAuraName`, as the dictionary keys their names go by) and whoever stands behind the warframe (`Operator`: the drifter when the loadout has an `OPERATOR_ADULT` key, the operator when it has `OPERATOR`, with the `FocusAbility` path either way). Each is an `Item` of internal path, rank (`Level`), forma (`Polarized`), the parts a modular item is built from (`ModularPartTypes`) and what is installed on it (`WeaponUpgrades`, a flat list of paths mixing cosmetics, mods and arcanes, the empty slots dropped; `names::Kind` tells them apart). The summary is lenient: whatever is missing or shaped otherwise is left out. It is also `#[serde(default)]`, since the history keeps summaries on disk and one written down before a field existed must still read. At start the worker hands back `self_latest.json` (`latest_own`), so our card is filled before the game shows our loadout again.

5. **`src/history.rs` — `History`**: everyone we have shared a squad with, as they were when it came apart. The monitor writes a member down when a mission's session ends with them in the squad, and when they drop out of the squad, with that moment as the match's time, kept both in seconds since the epoch and as the wall clock had it (`GetLocalTime`), so showing it later needs no calendar. A squad that stays together for several missions is written down once a mission, each time with the loadout it was played in, which is what a fixed squad changing gear between missions asks for. Members whose loadout was never captured are let go, and so are those tied to no mission (`MissionTracker::tie`), who left before any started: the history is for the loadouts players bring to missions. Each entry keeps the `location` (`SolNode228`) and `mission_type` (`MT_LANDSCAPE`), as the log's ids, of the mission the member was tied to when they left; both are empty only for entries written down before missions were (`#[serde(default)]`), when players who played none were kept as well. The newest `KEPT` (5000) live, newest first, in `history.json` beside the loadouts; a `LoadoutView` is what is written down, without the loadout's whole JSON, which would run to tens of megabytes and is in `loadouts` already. Each entry names the file it is in, so `files` and `horizon` tell `loadout::discard_unkept` which of them to spare; the monitor clears the folder out at start and after every departure it writes down, which is what keeps it from growing without end.

6. **`build.rs` and `src/names.rs` — display names.** `build.rs` reads the exports a loadout draws on from the submodule (`EXPORTS`: warframes, weapons with modular parts, companions, mods, arcanes, cosmetics, flavour, gear, resources, railjack weapons, avionics, focus, virtuals) along with `dict.<LANGUAGE>.json`, and writes `names.tsv` to `OUT_DIR`: one line per named item, sorted by path, as `path \t export \t part type \t name`, about 14,000 lines and 1.3 MB. Line breaks inside a name are folded into spaces. `LANGUAGE` is `en`, though the game here runs in Japanese (EE.log's `-language:ja`): Japanese names are taller than Latin ones, and a card with one in it would stand its rows at heights the cards beside it cannot match. Every dictionary is complete, so a language never falls back to another. `names.rs` embeds the table with `include_str!` and indexes it into a `HashMap` on first use. `lookup` returns an `Entry` of `Kind` (the export the item came from — what tells mods from arcanes and cosmetics), name, and the slot a modular part fills. `item_name` names a modular item after its defining part (`NAMING_PARTS`: a zaw's strike, a kitgun's chamber, an amp's prism, a MOA's or hound's model, a K-Drive's board), since bases such as the zaw's have no name of their own. Beasts bred from parts (antigen/mutagen) keep their own name. Two kinds of line name something other than an exported item's path, because a loadout does not go by one: every AURA mod in `ExportUpgrades` lends its dictionary key a line (export `Auras`, `Kind::Aura`), since `AuraName` gives the key, and each school the focus export has a folder for gets a line for `/Lotus/Upgrades/Focus/<School>/<School>FocusAbility` (export `FocusSchools`, `Kind::FocusSchool`), named as the dictionary names that school's operator ability (`Operator<School>AbilityName`), since no export lists the path `FocusAbility` gives. Two more kinds name what EE.log gives for missions (see `mission.rs`), by the log's ids rather than paths: every node of `ExportRegions` under export `Regions` (`Kind::Region`), named with its system as `Plains of Eidolon (Earth)` (`node_name`), and every mission type of `ExportMissionTypes` under `MissionTypes` (`Kind::MissionType`, `mission_type_name`), a name the dictionary gives in capitals (`FREE ROAM`) brought down to how the rest are written (`capitalised`, `Free Roam`). The export has the newest nodes and types (the Perita Rebellion's, Höllvania's), which WFCD's worldstate-data lags behind on; what it lacks, such as most event nodes, shows its id. Not every path in a loadout is in the export: pet claws, some titles, operator bases and default customisations stay unnamed. Every loadout item also carries a `LocTag` dictionary key; the table does not carry dictionary keys, so it is unused. `build.rs` declares `rerun-if-changed` on exactly the files it reads, so a `git submodule update --remote` is all it takes to refresh names; one run takes a couple of seconds. Built without the submodule, it only warns and embeds an empty table, and items fall back to the last segment of their path.

7. **`src/main.rs` — `OverlayApp` (eframe/egui)**: the UI thread. Each frame it drains the snapshot channel (keeping only the latest), repositions/resizes the window to hug the bottom of the game window using `window_rect` from the snapshot, and toggles window visibility only once a `window_rect` is known (to avoid flashing at a stale position). **All sizes in this file are authored against a 2560x1440 Warframe client area**: `ui_scale` derives a factor from `window_rect.height / 1440` and feeds it to `Context::set_pixels_per_point`, so fonts, margins and `OVERLAY_HEIGHT` scale as one. This deliberately overrides monitor DPI — the overlay's proportions follow the game's resolution, not the desktop scaling. Geometry sent via `ViewportCommand` is computed with that same factor rather than `Context::pixels_per_point()`, because egui-winit applies viewport commands using the *new* zoom (a fresh `set_pixels_per_point` does not land in `pixels_per_point()` until the next pass). The overlay normally repaints twice a second (`request_repaint_after(500ms)`); a location line wider than `LOCATION_MAX_WIDTH` scrolls instead of being truncated, and asks for `MARQUEE_FRAME_INTERVAL` (10 fps) for as long as it is on screen. Because of that raised rate, `PeerCard`s are rebuilt only when a snapshot arrives (flag SVGs are base64-decoded there) and the `InnerSize`/`OuterPosition` commands are sent only when `window_rect` actually changes — egui-winit turns each into an unconditional `SetWindowPos`. It has two render modes: a full status panel (shown when Warframe isn't actively being monitored, e.g. "waiting for Warframe") and a compact peer-card row (shown once EE.log is being monitored and peers exist). Window chrome: undecorated, transparent, always-on-top, taskbar-skipped, and mouse-passthrough is enabled after the first frame so it never intercepts game input. A tray icon (via `tray-icon`) provides the only way to exit, since there's no visible window chrome. It is also where the language is chosen: `main` puts what `lang::load` read in force before the single-instance check, and a `SetLanguage` for the other one saves it, raises a flag and closes the root viewport. Once `run_native` has returned, `main` drops the `SingleInstance` guard — the new process goes looking for that name straight away — and `relaunch` starts the exe again with the arguments it was given. Restarting rather than re-laying the windows in place is deliberate: they measure their columns against the text they hold, and a `ViewportBuilder` is only honoured on the pass that makes the window. Japanese-capable fonts are loaded from `%WINDIR%\Fonts` (falls back through Noto Sans JP VF / Yu Gothic / Meiryo / MS Gothic) since peer/status text can be Japanese. It also hosts the loadout windows, handing them each snapshot's `LoadoutView`s and history and running them on every pass, ahead of the overlay's own early return.

8. **`src/loadout_window.rs` — `LoadoutWindow`** (a module of the binary, next to `main.rs`): five ordinary decorated, resizable windows, each run as an egui *immediate* viewport of the root, so they are drawn during the root's pass. A `Layout` (`COMPACT`, `FULL`, `GRID`, `HISTORY`, and the debugging `SESSION`, see `mission.rs`) is all that tells them apart: the viewport id, the title, the size it opens at, and the function that draws the rows. Each is created on the first tray click asking for it and not before. Closing it sends `Visible(false)` rather than letting the viewport go, and later clicks send `Visible(true)`/`Minimized(false)`/`Focus`, so it keeps its place and size for the session. Where the user leaves it is written down once the drag comes to rest (`remember`) to `windows.json` beside the loadouts — its corner in desktop pixels, its size in desktop points — and it opens there on the next run: the builder makes a guess at the corner, and `place` moves the window onto it once the window exists and says what scale its monitor has (see the gotchas). A stored corner whose title-bar strip no monitor shows (`on_screen`), as when the monitor it was on is gone, is dropped, and the window opens where Windows puts a new one. Its `ViewportBuilder` is built once and passed unchanged every pass (see the gotchas). **Every size in this file goes through `Scale` (1 / zoom factor)**, the counterpart of the overlay's `ui_scale`: it leaves the window at its own monitor's DPI whatever the game's resolution. **Every word it writes itself comes from `lang::text`** — `text::gear_slots()` for the slot labels, `text::you()` for the mark on our own card, and so on — so the Japanese quoted below is the original each was written as, with an English counterpart beside it in `lang.rs` that is what the overlay shows by default. `COMPACT` lays out one card per `LoadoutView`: a header line (name, MR, platform, New War / Old Peace, and pinned to its right end where the peer connects from — `region, country` and that country's flag, which our own card never has) over an equipment line (warframe, primary, secondary, melee, companion), with a note in place of the latter until the loadout is captured. `show_header` gives the location whatever room the header cells leave, so a narrow window pushes it onto the next line instead of shrinking anything; the flag SVG is the overlay's own `flag_icon_bytes`. Each line's columns line up from card to card (`column_widths` takes each column's widest galley), and `horizontal_wrapped` wraps a line when the window is too narrow. Items are labelled by `names::item_name`, falling back to the last segment of the internal path (`item_label`). Hovering shows the internal path, a modular item's parts, rank and forma. A right-click on a card copies that player's whole loadout, the `RawJson` the monitor carries alongside the summary, laid out over several lines (`copy_on_right_click`). It reads the pointer out of the input rather than putting a widget over the card, which would take the hovering away from everything underneath. The full layout (`show_full_cards`) stands a tall card per player side by side instead — `CARD_WIDTH` each, four to the 1440 points that window opens at — opening with three lines of its own (`HOST` and the mark that a card is ours on the left with the name against the right edge; mastery rank and platform on the left with the quests against the right edge; then the flag and where the peer connects from), and then, each under a rule of its own, every slot with its name against the right edge and the mods and arcanes installed on it underneath, two to a row, each kept once however often the game lists it and in a block `MOD_ROWS` tall whatever the player has on, so the slots line up from card to card. A mod name too long for its column, or an item name too long for what its label leaves it, is cut short with an ellipsis (`TextWrapping::truncate_at_width`) — running over would cross into the column beside it, and wrapping would cost a mod block a row it has kept no room for; the whole of either is a hover away (`mods` picks the `names::Kind::Mod` and `Kind::Arcane` entries out of the cosmetics sharing `WeaponUpgrades`, and falls back to the end of the path for one the export does not name). The layouts build their text from the same pieces: the jobs `header` is made of (`name_job`, `mastery_job`, `platform_job`, `host_job`, `quest_jobs`), `gear`, `item_label` and `item_details`. `GRID` (`show_grid_cards`) splits the window into six places, three to a row, and fills them in the squad's order, outlining a place nobody has taken as `未参加`. Each card opens with a header of its own, two lines tall and in three columns (`show_grid_header`): `HOST` and our mark over mastery rank and platform on the left, each line keeping its height when empty; the region over the country and its flag against the right edge (`place_lines`, which says a region that is the country itself once, on the flag's line, but keeps one that only shares a word with it, such as Mexico City; lines longer than `GRID_PLACE_WIDTH` are cut short); and between them the name, at `GRID_NAME_SCALE` of the size that would make one line of it as tall as the two beside it, so it does not crowd them, centred on the card as far as the sides leave room. The sides are laid into child `Ui`s over each line and measured, which is how the name learns that room. It has no location line and no quests. Every grid card has a stroke as wide as our gold one, transparent on the others, because a frame sets its contents in by its stroke's width and the rows would otherwise stand a pixel apart. It puts its gear beneath in two columns split down the middle (`GRID_GEAR`: warframe and primary, secondary and melee, companion and the extras), with the same slot lines and `MOD_ROWS` blocks. The extras (`show_grid_extras`) come in two blocks: the auras, labelled and named as a slot is, a second one on a line of its own, and left out whole when there is none; then the operator or drifter with their focus school, left out when the loadout has neither, followed by the quests against the right edge as part of that block. A rule parts the two only when both an aura and an operator line are there. `grid_fit`'s sample carries two auras and an operator, the tallest this column gets. The places follow the window's size, and so does what is drawn in them: `grid_fit` lays a sample card with a captured loadout out of sight (an `invisible` child `Ui` clipped to nothing, so it is neither painted nor hoverable) to learn how tall a card stands at its designed size, and draws every card at the largest twentieth (`FIT_STEPS`) of that size which fits both its width (`GRID_WIDTH`) and its height, through a `Scale` multiplied by it (`Scale::times`). Stepping keeps a window being resized from laying text out afresh at every size it passes through; a card's own clip rect cuts off whatever still overflows. `HISTORY` puts everyone met before down the left — name, mastery rank, platform, the node and type of the mission they were tied to (`mission_labels`: named through `names`, the id where the export lacks it, `—` for none, the whole of either and the ids a hover away where a column cuts them short), flag and when the squad came apart, only the rows on screen laid out (`show_rows`), since there can be a thousand — and what they add up to on the right (`show_statistics`), in a grid of cells four wide and two tall (`STATS`, in the order of `Statistic::index`): platforms, countries, focus schools and warframes over primaries, secondaries, melee and companions. `tally` counts every entry as often as the player was met, under what `Statistic::key` gives for it (a platform, a country code — the name where there is none — a focus school's path, an item's `item_label`), and against the right end of the header line (see below) stands what they add up (`show_scope`, `統計表示対象データ：[全データ / 検索データのみ]`): every entry (`Scope::All`), or only those the list shows as the filters narrow it (`Scope::Listed`). `refresh_tally` works it out again only when the snapshot hands over another history (`Arc::ptr_eq`), the scope changes, or, under `Listed`, the filter does; `refresh_listed` sifts the list the same way (`Shown::listed`). The statistics are drawn before the filters that change in the same pass, so under `Listed` a changed filter asks the root viewport for another pass. Platforms (in `platform_color`) and focus schools (`focus_color`; entries without an operator are left out) are pies, painted as a triangle-fan `Mesh` with lines in the cell's colour between slices and round the rim, since a mesh has no anti-aliasing of its own; hovering a slice names it (`slice_at`). Countries (with their flags; regions are not counted) and each slot are rankings, most first, those counted as often sharing a rank, over a bar as long as its share of the first's; a slot's shares are out of the players whose loadout was kept. Every slice and line is a toggle: what is picked (`Filter::picked`, gold-outlined, the unpicked slices dimmed) narrows the list to players matching one of the picks in each kind that has any, and by the filters of the header line (`show_history_header`, one line as tall as a box to type in (`filter_height`) across both sides). Over the list stand the filters of its columns (`show_list_filters`), each lined up with the column's cells (set in by `ROW_MARGIN`, as a row's are): a box for the name over the columns that say who a player was, one for the mission's node over its column, matched against the node's name or its id (`SolNode228`), both ignoring case, and a menu of every mission type the export names (`names::mission_types`, by name) over theirs, held to the column's width with its list as wide as the longest name. Then come the dates a match must fall between (`show_dates`), picked from `egui_extras`' calendar (`DatePickerButton`, whose `datepicker` feature brings `jiff` in for the dates themselves), each unset for no bound and both part of the range (`within`, against the wall clock an entry was written down by, which sorts as it runs and so needs no calendar to compare). A picker's button says which end of the range it is until a date is picked for it, a format being written out as it stands but for what follows a `%`, and the cross beside a date picked lets it go. `絞り込み解除` follows the dates, and the line runs on past the list from the dates onwards, there being no room over it for two of them. All of it goes through `Filter::apply`; `絞り込み解除` lets it all go, the picks included. The statistics are drawn before the list so that a pick narrows it in the same pass. A click on a row lays that player's card over the statistics (`show_chosen`): a grid card through `show_grid_card`, at the largest `fit` step up to its designed size, on a `VEIL`, in an `egui::Area` of its own so what it covers takes no pointer. A click anywhere but on the card, the same row again, or Esc puts it away; another row puts that player's card in its place.

9. **`src/mission.rs` — `MissionTracker`**: which mission each squad member is tied to, for the `History` to write down as they leave. Like `LogParser`, a pure state machine over EE.log lines, fed the same lines by `read_appended_lines` but kept apart from it, since the parser clears on leaving a squad and a mission goes on regardless. Loading a mission logs a line ending in `with MissionInfo:` — `ThemedSquadOverlay.lua: Host loading {...}` or `EidolonMP.lua: Host entering plains` as the host, `Client loaded {...}` as a client, the `{...}` JSON naming the node (`"name"`; a client entering an open world is handed the hub's, `CetusHub4_HUB`) — followed by a block of its details on lines without timestamps: Lua-like from a host (`    missionType=MT_DESCENT`), JSON from a client (`    "missionType" : "MT_EXTERMINATION",`). Only fields indented exactly four spaces are the mission's own (a client's block nests others, such as `missionReward`); the block closes with `}` at the start of a line, or at the next timestamped line, and only then is the mission kept — and only if its location has `Node` in it (`is_node`: `SolNode228`, `CrewBattleNode501`, `EventNode12`): hubs (`CetusHub4`, relays, `1999Hub`) load the same way and are let go. A session ends at `Sys [Info]: EOM missionLocationUnlocked=<n>`, which a host logs even on aborting, or at `TopMenu.lua: Abort:`, since a client aborting (`client/session/PVP`) logs no EOM; the first end stands. `tie_squad`, called after every line that changed the squad or the missions (line by line, so the whole log replayed at start ties members as it went), ties everyone in the squad bar ourselves to the mission whose session is going on (`ongoing`); a tie outlives the session's end and the member's leaving, until another session ties them afresh, and whoever joins while no session goes on — or joins again after leaving — starts untied. So a member met between sessions who leaves before one starts is not written down at all: the history is for the loadouts players bring to missions. `sessions_ended` tells the monitor when a session has ended since it last asked, so it can write down everyone the session tied; the first time it is asked after a log read from its start it reports nothing and lets go of every tie but one to a session still going on, since the run that watched those end is the one that wrote them down. `restart` (Warframe stopping, the log shrinking) forgets the missions and the squad but keeps the ties, for the departures that restart brings on. The last `RECENT` (10) missions and the squad's ties go into the snapshot (`MonitorSnapshot::missions`/`squad_ties`, both part of its signature) for `SESSION`, a debugging `LoadoutWindow` layout that shows them in the log's own names and clock. Every load also logs a one-line `SyncAutoPopulatedConsumables for mission <type> with location <node>`, should the block ever prove harder to read.

Data flow in one line: `EE.log` → `monitor::read_appended_lines` → `parser::LogParser::process_line` → `monitor::run` (adds geo via `GeoResolver`) → `MonitorSnapshot` over `mpsc::Receiver` → `OverlayApp::ui` renders `PeerView`s and hands `LoadoutView`s to `LoadoutWindow`, which names their items through `names`. Announced and changed member loadouts and our own rebuilds branch off in `monitor::run` → `loadout` worker → JSON files, and come back as `Captured` → `monitor::loadout_views`.

10. **`src/tray.rs`** — the tray icon and its menu (`Loadouts`, `Loadouts (full)`, `Loadouts (6grid)`, `History`, `Session (debug)`, a separator, the `Language` submenu, a separator, `Exit`), on a thread of its own with a plain `GetMessageW` pump. The thread is load-bearing (see the gotcha below), not incidental. `build_menu` puts it together apart from the pump, which is what lets a test look at what it holds without an icon in the notification area; it keeps each plain item's `MenuId` beside the `Command` it stands for, and the two `CheckMenuItem`s of the `Language` submenu, whose labels are the languages' own names (`日本語`, `English`) in either language and which open with the one in force ticked. It hands each choice to an `on_command(Command)` callback. For each `Show…` command, `main.rs` raises that window's show flag and requests a repaint of the root viewport; for `Exit`, it closes the root viewport. Both are safe from another thread because `egui::Context` is `Send + Sync`. A `Language` click sets both ticks from the choice rather than leaving the one Windows toggled, then hands over `SetLanguage`, which `main.rs` ignores when it names the language already in force. `icon_rgba` decodes the icon for the tray and for the loadout windows' title bars and taskbar entries alike.

11. **`src/single_instance.rs`** and **`src/notify.rs`** — process-lifecycle concerns, both claimed in `main()` before `eframe::run_native`. `SingleInstance` holds a `Local\WarframePeerOverlay` named mutex whose guard must live for the whole process (dropping it frees the name); a refused launch shows a toast instead of exiting silently, because a release build has no console to print to. `notify::show` returns `Result` so callers choose how to handle failure.

12. **`src/lang.rs` — `Language` and `text`**: which of the two languages every window is written in, and the words themselves. Japanese is what the windows were laid out and sized against, so it is the original of each pair; English is the translation, kept beside it line for line by the `words!` macro (`name = (japanese, english);`), which makes each one a function returning `&'static str`. The words that take an argument (`text::rank`, `text::player_count`, `text::record_count_listed`) are written out by hand beneath, since a number sits in a different place in each language. `Language::DEFAULT` (English, which more of the people this is handed to read) is what the overlay opens in until a language is chosen; it sits beside the `#[default]` so the atomic below can start from it. The choice lives in a process-wide `AtomicU8` rather than being threaded through every function — the words are wanted deep inside layout code, on the UI thread and the monitor thread alike — and is written down in `settings.json` beside the loadouts (`load`/`save`), read back by `main` before anything is shown. Nothing has to cope with the language moving under it: a change from the tray restarts the overlay. Only what the project writes itself is here. Names the game gives come from the export's `en` dictionary in either language (see `names`), and so do `HOST`, `MR`, platform names and the windows' titles. The one place the language would otherwise leak into logic is the overlay's status line, which is why `monitor::Status` is an enum with a `Display` through `text` rather than a `String` the UI compares against.

`src/lib.rs` re-exports every module except the UI — `main.rs` and its submodule `loadout_window.rs` — so the library stays free of egui; `main.rs` and the test modules use the rest as `warframe_peer_overlay::*`.

## Windows gotchas learned the hard way

- **Release builds set `windows_subsystem = "windows"`** via `#![cfg_attr(not(debug_assertions), ...)]` at the top of `main.rs`, so no console window appears behind the overlay. Debug builds keep the console for `cargo run`. Verify with the PE subsystem byte: `2` = GUI, `3` = console.
- **A toast is dispatched asynchronously.** If the process exits right after `notify::show`, WinRT drops it before delivery and nothing appears. The single-instance rejection path sleeps ~1s before returning for exactly this reason. To check delivery on a machine, watch `%LOCALAPPDATA%\Microsoft\Windows\Notifications\wpndatabase.db-wal` for a write, or run `cargo test --lib -- --ignored show_`.
- **Toasts need a registered AppUserModelID**, which a portable exe has none of; `notify.rs` borrows `Toast::POWERSHELL_APP_ID`, the standard fallback. COM apartment init is not needed — `windows-core`'s factory cache falls back to `CoIncrementMTAUsage`.
- **The tray icon is `assets/icon.png`, embedded with `include_bytes!`** so the release exe stays a single portable file with no assets directory to ship. It is decoded with `image` (png feature only) into RGBA (`tray::icon_rgba`), for `tray_icon::Icon::from_rgba` and the loadout window's `IconData`. The names table is embedded for the same reason.
- **The tray icon must not share winit's thread.** `tray-icon` opens its context menu with `TrackPopupMenu`, which runs a modal message loop on the thread owning the tray window. Under eframe/winit that loop receives no mouse or keyboard input at all: the menu appears, nothing highlights on hover, and clicking an item just dismisses it without emitting a `MenuEvent`. The same menu driven by a bare `GetMessageW` pump works, and so does the menu when the tray lives on its own thread — which is why `tray.rs` owns one. Do not "simplify" it back onto the UI thread.
- **To test the tray menu without a mouse**, find the tray window by class name `tray_icon_app` for the process, `PostMessageW(hwnd, 6002, 0, WM_RBUTTONUP)` (6002 is tray-icon's `WM_USER_TRAYICON`) to open the menu, then drive it with `keybd_event` VK_DOWN/VK_RETURN: VK_DOWN once reaches `Loadouts`, twice `Loadouts (full)`, three times `Loadouts (6grid)`, four times `History`, five times `Session (debug)`, six times `Language`, seven times `Exit` (separators are skipped). `Language` is a submenu, so VK_RIGHT opens it and VK_DOWN then reaches `日本語` and `English` in turn. That only works while the menu has foreground. muda asks for it with `SetForegroundWindow`, and in practice gets it only when the overlay already owns the window in front, such as an active loadout window. Otherwise the keystrokes land in whatever is in front (the game, the editor), so check `GetForegroundWindow` first and leave it to a real click when the overlay is not in front. Nothing else drives the menu. A `WM_KEYDOWN` posted to the menu window (class `#32768`) is ignored. muda shows context menus with `TrackPopupMenu(TPM_RETURNCMD)` and handles the choice inline, so a `WM_COMMAND` posted to the tray window does nothing either. While the menu is open, `MN_GETHMENU` and `GetMenuItemID` read its items, which is enough to check what it contains; `WM_CANCELMODE` to the tray window closes it.
- **A window's position must be kept in pixels, not points, across monitors of different scale.** A point is a different number of pixels on each monitor, and winit turns a position given in points (`ViewportBuilder::with_position`) into pixels at the scale of the monitor the window is *created* on — the primary, where Windows puts a new window — not the one it is going to. Stored in points, a History window left at 100% beside a 150% primary opened half as far out again, off every monitor: a blank entry in Alt+Tab that Win+arrow could not bring back. Hence `Scale::to_pixels`/`to_points` with the viewport's `native_pixels_per_point`, and `place` correcting the corner a pass after creation. A programmatic move across monitors keeps the window's corner where it was asked for; winit's `WM_DPICHANGED` handler then rescales the size to keep it in points.
- **egui's zoom factor is global across viewports.** `set_pixels_per_point` is really `set_zoom_factor`, so the overlay's game-driven scale also scales the loadout window — hence `Scale` in `loadout_window.rs`. For the same reason the loadout window's `ViewportBuilder` is built once: egui re-applies a builder that differs from last pass, and one sized under a new zoom would undo the user's resizing.
- **eframe keeps running the root's `ui` while the overlay is hidden.** It skips a viewport's pass only when the viewport is minimized or occluded, not when it was hidden with `Visible(false)`. That is what lets the overlay show itself once the game appears, and what lets a tray click open the loadout window while the overlay is hidden. A child viewport that goes one pass without `show_viewport_*` is destroyed, so `LoadoutWindow::show` must run on every pass.
- **`configure_style` forces the dark theme.** Only the dark style is customised, and following a light Windows theme would also draw the loadout window's scroll bar and tooltips light.
- **A restart has to let the single-instance name go first.** `SingleInstance` holds the `Local\WarframePeerOverlay` mutex, and Windows keeps the name reserved only while a handle to it is open. `main` therefore drops the guard as soon as `run_native` returns and before `relaunch` spawns the exe again, or the new process would find the name taken, show the "already running" toast and exit — leaving the user with no overlay at all.
- **The submodule is shallow** (`shallow = true` in `.gitmodules`): `git submodule update` fetches one commit rather than the export's ~110 MB of history.
- **`BuildLoadOut for <name>` is not only about us.** The game builds squad members' loadouts locally as well, and each build leaves a version of theirs in memory — which is why `LogParser` counts our own rebuilds apart from everyone else's (`own_builds`/`other_builds`), and why the worker is sent to take note after a foreign one.
- **Temp file and directory names in tests must not contain `::`** — Windows rejects them, which is why the `monitor` tail test and the `loadout` save tests build their names from the pid rather than the thread name.
- **The loadout reader is tested against the test process itself** (`reads_a_loadout_back_out_of_a_live_process`), which exercises the real `OpenProcess`/`VirtualQueryEx`/`ReadProcessMemory` path without the game. In the live app, members who joined before the overlay started are still requested (the whole log is replayed at start), but are saved only if their string is still in memory.
