# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Windows-only native overlay that shows Warframe squad peer info (platform, name, host status, and optional country/region/ASN) anchored to the bottom of the game window. It detects the `Warframe.x64.exe`/`Warframe.exe` process, tails `%LOCALAPPDATA%\Warframe\EE.log`, and renders a borderless, click-through, always-on-top window with a tray icon for exit. In the background it also saves mission loadouts as JSON, read out of the game's memory (read-only): each squad member's once EE.log announces that they joined, and our own every time EE.log shows it rebuilt. A second, ordinary window — hidden until the tray menu's `Loadouts` opens it — shows those loadouts as one card per player, ours on top, with items named as the game names them, from the public export vendored as a submodule.

Privacy model (see README.md): log parsing and host detection are entirely local. If geo lookups are enabled (default), only the detected public IP is sent to `https://ipinfo.io`; results are cached on disk for 30 days. Loadout capture opens the game process with `PROCESS_VM_READ | PROCESS_QUERY_INFORMATION` only — it never writes, injects or hooks — and saves loadouts, with display name and platform, under `%LOCALAPPDATA%\synqark\WarframePeerOverlay\data\loadouts`; none of it is uploaded. Item names are embedded at build time, so looking them up sends nothing anywhere. EE.log contents and IPs are never logged or uploaded. `--no-geo` disables the external lookup entirely.

## Commands

```powershell
git submodule update --init   # fetches third_party/warframe-public-export-plus (shallow); the build embeds item names from it
git submodule update --remote # moves it to the latest export after a game update; the next build picks it up
cargo build --release   # produces target\release\warframe-peer-overlay.exe
cargo run                # debug build + run (Windows only — uses windows-sys/tray-icon/winit)
cargo test                # runs all unit tests (every module has a #[cfg(test)] block)
cargo test <test_name>    # run a single test by name, e.g. `cargo test joins_member_ip_and_host_when_events_arrive_out_of_order`
cargo test --lib -- --ignored show_   # opt-in: pops a real desktop toast to verify notifications
cargo clippy --all-targets # lint
cargo fmt --all --check    # CI enforces this
```

The binary must be built/run on Windows — it links `windows-sys` APIs directly (window enumeration, positioning, process memory reads) and uses `tray-icon`/`winit` Windows integration.

CI (`.github/workflows/ci.yml`) checks out the submodule and runs fmt/clippy/test/build on `windows-latest` with `RUSTFLAGS: -D warnings`; keep all four green. Pushing a `v*` tag triggers `release.yml`, which attaches the exe to a GitHub Release.

## Licensing and game data

This is a personal-use tool with no plans to be published, so game-derived strings and data may live in the repository and be embedded in the exe. In particular, `third_party/warframe-public-export-plus` is a git submodule of [calamity-inc/warframe-public-export-plus](https://github.com/calamity-inc/warframe-public-export-plus) — Digital Extremes' public export, reorganised and completed, with no license of its own — and the exe embeds item names taken from it. The Unlicense in `LICENSE` covers this project's own code, not the submodule or the data drawn from it. Tests may use real game paths and names. `assets/icon.png` is original artwork drawn for this project (a four-node squad graph in the overlay's gold/navy palette).

What stays out of the repository is other players' data: tests build their own minimal loadout JSON and log lines, never a captured loadout or a log sample with real player names.

## Architecture

The app is a background monitor thread feeding a UI thread over an `mpsc` channel, with a strict pipeline for turning raw log lines into on-screen peer cards. Off to the side, a capture worker thread takes loadout jobs from the monitor, writes what it finds to disk, and hands each find back to the monitor for the loadout window.

1. **`src/parser.rs` — `LogParser`**: a pure state machine over EE.log lines. It has no I/O; `process_line(&str) -> bool` returns whether the parseable peer state changed. It correlates several independently-arriving log line types (`AddSquadMember`, `Squad host address`, `Added remote player`, `VOIP: Registered remote player`, `Received ping from`) into a `Vec<Peer>`, because Warframe emits a peer's name, matchmaking ID, and IP on different lines in unpredictable order. `reconcile()` re-derives each peer's IP and host status every time new correlating data arrives; host detection falls back to "the locally logged-in user is host" only when no remote peer's IP matches `Squad host address`. Player names embed a private-use-area codepoint (e.g. `\u{e001}`) as a platform suffix — decoded in `parse_player_name`. It also keeps the loadout size each member's `ProcessSquadMessage received JOIN message from <name>, loadout: <N> bytes` line announces (`Peer::loadout_bytes`); that line arrives just before the member's `AddSquadMember`, so the size is held by name and applied in `reconcile()` like the ping IPs. For our own loadout it counts `BuildLoadOut for <local user>` lines (`own_builds`) — every change in the arsenal, leaving it, and loading into a mission rebuilds it — and remembers our platform from our own `AddSquadMember` (`local_platform`); neither is reset by `clear()`.

2. **`src/geo.rs` — `GeoResolver`**: given a public IP, queries `ipinfo.io` for country/region/org, skips private/loopback/documentation IPs, and caches results (with a `fetched_at` timestamp, 30-day TTL) to a JSON file under the OS cache dir (via `directories::ProjectDirs`, `com.synqark.WarframePeerOverlay`). `looks_like_hosting_provider` matches the ASN org name against a hardcoded list of cloud/hosting providers to flag likely relay/VPN peers (`is_hosting`) — this is a heuristic, not a definitive VPN detector. Entirely bypassed when `--no-geo` is passed.

3. **`src/monitor.rs` — `spawn`/`run`**: owns the background thread. On a 500ms loop it: (a) polls `sysinfo` for the Warframe process, (b) if running, finds its main visible window's client rect via `EnumWindows`/`GetClientRect`/`ClientToScreen` (used by the UI to position the overlay under the game window), (c) tails `EE.log` by tracking a byte offset and only feeding *complete* lines to `LogParser` (partial trailing lines are buffered in `pending` until the next newline arrives — see `read_appended_lines`), (d) hands the capture worker every newly announced member loadout — once per name and size, never for the local user (`capture_requests`) — and our own loadout whenever `own_builds` has moved (`own_request`; right after start-up that is immediately, as the log replay counts every rebuild so far), then drains what the worker has captured, (e) resolves geo info for any new peer IPs via `GeoResolver`, and (f) builds a `Vec<PeerView>` (the parser's `Peer` plus resolved geo/UI fields) and the loadout window's `Vec<LoadoutView>` (`loadout_views`: ours always first — the latest own capture, else a placeholder from the parser — then every member still in the squad, matched to a capture by name *and* announced size, so a member who re-joins with other gear is not shown the old one; a member's card goes when the parser drops them), and sends a `MonitorSnapshot` through the channel — but only when a signature (debug-formatted state) differs from the last sent snapshot, to avoid needless UI churn. State resets (log offset, parser, geo failure cache, requested and captured member loadouts) whenever Warframe stops running; our own capture is kept. The log offset and parser also reset when the log file shrinks (log rotation).

4. **`src/loadout.rs` — capture worker**: a loadout lives in the game's heap as a NUL-terminated JSON string starting with `{"PlayerLevel":` (warframe and weapons with their mods, forma and levels, companion, archwing, operator, gear, focus). One pass over the game's committed, readable, non-code regions (`VirtualQueryEx`, then `ReadProcessMemory` in 32 MB chunks) collects every such string that ends in `}` right before its terminator and parses, counting identical copies (`census`). That serves both kinds of job: a member's loadout is the string of exactly the size their JOIN line announced (`pick_member`); ours is the most-copied version no earlier pass has met — the rebuild itself, which appears within the same second as `BuildLoadOut` — or, when there is none, the most-copied version overall, since superseded versions are freed within minutes (`pick_own`). Versions saved for members are never taken for ours. No struct layouts or pointers are involved, so a game update that moves memory around does not break it. A pass reads several GB and takes a second or two, hence the thread of its own: jobs arriving together share one pass, a member is retried every 2 s for 20 s, and our own rebuild gets a second pass when the first finds nothing new. Members are written as `<unix time>_<name>_<platform>.json`; ours as `self/<unix millis>.json` plus `self_latest.json`, which is written aside and renamed over so a reader never sees half a file. Every file wraps the loadout with name, platform, size and capture time. Every find is also handed back over a second channel as a `Captured`, carrying a `Loadout` summary (`Loadout::from_json`): mastery rank, the `PostNewWar`/`PostOldPeace` quest flags, the warframe, secondary, primary and melee from `NORMAL` slots 0–3, and the companion from `SENTINEL[0]` with its `KubrowName`. Each is an `Item` of internal path, rank (`Level`), forma (`Polarized`) and, for a modular item, its parts (`ModularPartTypes`, a list of part paths). An item's `WeaponUpgrades` are not kept yet — a flat list of paths mixing cosmetics, mods and arcanes, with `""` for an empty slot, which `names::Kind` tells apart. The summary is lenient: whatever is missing or shaped otherwise is left out. At start the worker hands back `self_latest.json` (`latest_own`), so our card is filled before the game shows our loadout again.

5. **`build.rs` and `src/names.rs` — display names.** `build.rs` reads the exports a loadout draws on from the submodule (`EXPORTS`: warframes, weapons with modular parts, companions, mods, arcanes, cosmetics, flavour, gear, resources, railjack weapons, avionics, focus, virtuals) along with `dict.<LANGUAGE>.json`, and writes `names.tsv` to `OUT_DIR`: one line per named item, sorted by path, as `path \t export \t part type \t name`, about 14,000 lines and 1.3 MB. Line breaks inside a name are folded into spaces. `LANGUAGE` is `ja`, the game's own setting here (EE.log's `-language:ja`). The Japanese dictionary is complete, keeping in English whatever the game leaves untranslated, so no fallback language is needed. `names.rs` embeds the table with `include_str!` and indexes it into a `HashMap` on first use. `lookup` returns an `Entry` of `Kind` (the export the item came from — what tells mods from arcanes and cosmetics), name, and the slot a modular part fills. `item_name` names a modular item after its defining part (`NAMING_PARTS`: a zaw's strike, a kitgun's chamber, an amp's prism, a MOA's or hound's model, a K-Drive's board), since bases such as the zaw's have no name of their own. Beasts bred from parts (antigen/mutagen) keep their own name. Not every path in a loadout is in the export: pet claws, focus schools, some titles, operator bases and default customisations stay unnamed. Every loadout item also carries a `LocTag` dictionary key; the table does not carry dictionary keys, so it is unused. `build.rs` declares `rerun-if-changed` on exactly the files it reads, so a `git submodule update --remote` is all it takes to refresh names; one run takes a couple of seconds. Built without the submodule, it only warns and embeds an empty table, and items fall back to the last segment of their path.

6. **`src/main.rs` — `OverlayApp` (eframe/egui)**: the UI thread. Each frame it drains the snapshot channel (keeping only the latest), repositions/resizes the window to hug the bottom of the game window using `window_rect` from the snapshot, and toggles window visibility only once a `window_rect` is known (to avoid flashing at a stale position). **All sizes in this file are authored against a 2560x1440 Warframe client area**: `ui_scale` derives a factor from `window_rect.height / 1440` and feeds it to `Context::set_pixels_per_point`, so fonts, margins and `OVERLAY_HEIGHT` scale as one. This deliberately overrides monitor DPI — the overlay's proportions follow the game's resolution, not the desktop scaling. Geometry sent via `ViewportCommand` is computed with that same factor rather than `Context::pixels_per_point()`, because egui-winit applies viewport commands using the *new* zoom (a fresh `set_pixels_per_point` does not land in `pixels_per_point()` until the next pass). The overlay normally repaints twice a second (`request_repaint_after(500ms)`); a location line wider than `LOCATION_MAX_WIDTH` scrolls instead of being truncated, and asks for `MARQUEE_FRAME_INTERVAL` (10 fps) for as long as it is on screen. Because of that raised rate, `PeerCard`s are rebuilt only when a snapshot arrives (flag SVGs are base64-decoded there) and the `InnerSize`/`OuterPosition` commands are sent only when `window_rect` actually changes — egui-winit turns each into an unconditional `SetWindowPos`. It has two render modes: a full status panel (shown when Warframe isn't actively being monitored, e.g. "waiting for Warframe") and a compact peer-card row (shown once EE.log is being monitored and peers exist). Window chrome: undecorated, transparent, always-on-top, taskbar-skipped, and mouse-passthrough is enabled after the first frame so it never intercepts game input. A tray icon (via `tray-icon`) provides the only way to exit, since there's no visible window chrome. Japanese-capable fonts are loaded from `%WINDIR%\Fonts` (falls back through Noto Sans JP VF / Yu Gothic / Meiryo / MS Gothic) since peer/status text can be Japanese. It also hosts the loadout window, handing it each snapshot's `LoadoutView`s and running it on every pass, ahead of the overlay's own early return.

7. **`src/loadout_window.rs` — `LoadoutWindow`** (a module of the binary, next to `main.rs`): an ordinary decorated, resizable window, run as an egui *immediate* viewport of the root, so it is drawn during the root's pass. The window is created on the first `Loadouts` click and not before. Closing it sends `Visible(false)` rather than letting the viewport go, and later clicks send `Visible(true)`/`Minimized(false)`/`Focus`, so it keeps its place and size for the session (not across restarts). Its `ViewportBuilder` is built once and passed unchanged every pass (see the gotchas). **Every size in this file goes through `Scale` (1 / zoom factor)**, the counterpart of the overlay's `ui_scale`: it leaves the window at its own monitor's DPI whatever the game's resolution. One card per `LoadoutView`: a header line (name, MR, platform, New War / Old Peace) over an equipment line (warframe, primary, secondary, melee, companion), with a note in place of the latter until the loadout is captured. Each line's columns line up from card to card (`column_widths` takes each column's widest galley), and `horizontal_wrapped` wraps a line when the window is too narrow. Items are labelled by `names::item_name`, falling back to the last segment of the internal path (`item_label`). Hovering shows the internal path, a modular item's parts, rank and forma.

Data flow in one line: `EE.log` → `monitor::read_appended_lines` → `parser::LogParser::process_line` → `monitor::run` (adds geo via `GeoResolver`) → `MonitorSnapshot` over `mpsc::Receiver` → `OverlayApp::ui` renders `PeerView`s and hands `LoadoutView`s to `LoadoutWindow`, which names their items through `names`. Announced member loadouts and our own rebuilds branch off in `monitor::run` → `loadout` worker → JSON files, and come back as `Captured` → `monitor::loadout_views`.

8. **`src/tray.rs`** — the tray icon and its menu (`Loadouts`, a separator, `Exit`), on a thread of its own with a plain `GetMessageW` pump. The thread is load-bearing (see the gotcha below), not incidental. It hands each choice to an `on_command(Command)` callback. For `ShowLoadouts`, `main.rs` raises the loadout window's show flag and requests a repaint of the root viewport; for `Exit`, it closes the root viewport. Both are safe from another thread because `egui::Context` is `Send + Sync`. `icon_rgba` decodes the icon for the tray and for the loadout window's title bar and taskbar entry alike.

9. **`src/single_instance.rs`** and **`src/notify.rs`** — process-lifecycle concerns, both claimed in `main()` before `eframe::run_native`. `SingleInstance` holds a `Local\WarframePeerOverlay` named mutex whose guard must live for the whole process (dropping it frees the name); a refused launch shows a toast instead of exiting silently, because a release build has no console to print to. `notify::show` returns `Result` so callers choose how to handle failure.

`src/lib.rs` re-exports every module except the UI — `main.rs` and its submodule `loadout_window.rs` — so the library stays free of egui; `main.rs` and the test modules use the rest as `warframe_peer_overlay::*`.

## Windows gotchas learned the hard way

- **Release builds set `windows_subsystem = "windows"`** via `#![cfg_attr(not(debug_assertions), ...)]` at the top of `main.rs`, so no console window appears behind the overlay. Debug builds keep the console for `cargo run`. Verify with the PE subsystem byte: `2` = GUI, `3` = console.
- **A toast is dispatched asynchronously.** If the process exits right after `notify::show`, WinRT drops it before delivery and nothing appears. The single-instance rejection path sleeps ~1s before returning for exactly this reason. To check delivery on a machine, watch `%LOCALAPPDATA%\Microsoft\Windows\Notifications\wpndatabase.db-wal` for a write, or run `cargo test --lib -- --ignored show_`.
- **Toasts need a registered AppUserModelID**, which a portable exe has none of; `notify.rs` borrows `Toast::POWERSHELL_APP_ID`, the standard fallback. COM apartment init is not needed — `windows-core`'s factory cache falls back to `CoIncrementMTAUsage`.
- **The tray icon is `assets/icon.png`, embedded with `include_bytes!`** so the release exe stays a single portable file with no assets directory to ship. It is decoded with `image` (png feature only) into RGBA (`tray::icon_rgba`), for `tray_icon::Icon::from_rgba` and the loadout window's `IconData`. The names table is embedded for the same reason.
- **The tray icon must not share winit's thread.** `tray-icon` opens its context menu with `TrackPopupMenu`, which runs a modal message loop on the thread owning the tray window. Under eframe/winit that loop receives no mouse or keyboard input at all: the menu appears, nothing highlights on hover, and clicking an item just dismisses it without emitting a `MenuEvent`. The same menu driven by a bare `GetMessageW` pump works, and so does the menu when the tray lives on its own thread — which is why `tray.rs` owns one. Do not "simplify" it back onto the UI thread.
- **To test the tray menu without a mouse**, find the tray window by class name `tray_icon_app` for the process, `PostMessageW(hwnd, 6002, 0, WM_RBUTTONUP)` (6002 is tray-icon's `WM_USER_TRAYICON`) to open the menu, then drive it with `keybd_event` VK_DOWN/VK_RETURN: VK_DOWN once reaches `Loadouts`, twice reaches `Exit` (the separator is skipped). That only works while the menu has foreground. muda asks for it with `SetForegroundWindow`, and in practice gets it only when the overlay already owns the window in front, such as an active loadout window. Otherwise the keystrokes land in whatever is in front (the game, the editor), so check `GetForegroundWindow` first and leave it to a real click when the overlay is not in front. Nothing else drives the menu. A `WM_KEYDOWN` posted to the menu window (class `#32768`) is ignored. muda shows context menus with `TrackPopupMenu(TPM_RETURNCMD)` and handles the choice inline, so a `WM_COMMAND` posted to the tray window does nothing either. While the menu is open, `MN_GETHMENU` and `GetMenuItemID` read its items, which is enough to check what it contains; `WM_CANCELMODE` to the tray window closes it.
- **egui's zoom factor is global across viewports.** `set_pixels_per_point` is really `set_zoom_factor`, so the overlay's game-driven scale also scales the loadout window — hence `Scale` in `loadout_window.rs`. For the same reason the loadout window's `ViewportBuilder` is built once: egui re-applies a builder that differs from last pass, and one sized under a new zoom would undo the user's resizing.
- **eframe keeps running the root's `ui` while the overlay is hidden.** It skips a viewport's pass only when the viewport is minimized or occluded, not when it was hidden with `Visible(false)`. That is what lets the overlay show itself once the game appears, and what lets a tray click open the loadout window while the overlay is hidden. A child viewport that goes one pass without `show_viewport_*` is destroyed, so `LoadoutWindow::show` must run on every pass.
- **`configure_style` forces the dark theme.** Only the dark style is customised, and following a light Windows theme would also draw the loadout window's scroll bar and tooltips light.
- **The submodule is shallow** (`shallow = true` in `.gitmodules`): `git submodule update` fetches one commit rather than the export's ~110 MB of history.
- **Temp file and directory names in tests must not contain `::`** — Windows rejects them, which is why the `monitor` tail test and the `loadout` save tests build their names from the pid rather than the thread name.
- **The loadout reader is tested against the test process itself** (`reads_a_loadout_back_out_of_a_live_process`), which exercises the real `OpenProcess`/`VirtualQueryEx`/`ReadProcessMemory` path without the game. In the live app, members who joined before the overlay started are still requested (the whole log is replayed at start), but are saved only if their string is still in memory.
